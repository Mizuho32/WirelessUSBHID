# USB Host側の実装

## Planning

### 概要
USB Host側の実装を行いたい。

### 要件
- USB Hostとして、(Hub接続もありうる)複数のUSB機器を受けたい
- 2026-08-21_filter_conv_route.mdで議論したように、filter/convが可能
- 送信機能
  - USB Deviceを直接つなぎ(UART, SPI?)、透過可能 (route)
    - CH9329, MAX3421(Hostだけど), あるいはesp32-kvm-ipに直接(かBluetooth)モード(slave)みたいなのを設ける?
  - server.pyのように指定ホストへ送信可能 (route)
  - 指定のサーバーへも送信可能 (route)

### 方針・要望
- まずHost→Deviceの透過機能を優先で実装。esp32-kvm-ipのBluetooth接続がハード実装なしでありがたい
- filter/convも欲しい。まずは.hにルール直書きが簡単?
- 実装はesp32-kvm-ip/内に可能? モード切り替えでHostにもDeviceにもなる、みたいだと一番丸い
- filter/convはHostに実装

### 回答・調査結果

#### 結論(最小コスト構成)
「新しいESP32-S3ボード1枚をUSB Hostにして、filter/conv後は**今ある`esp32-kvm-ip`のDevice側ファームをそのまま(無改造で)WiFi/UDPの受け側として使う**」のが圧倒的に最小コスト。理由:

- 受信側(`network_task.c`/`hid_task.c`/`protocol.h`)は今のまま1行も変えなくていい。単にHost側から今と同じ16バイトUDPパケットを、既存の`esp32-kvm-ip`機の IP:4210 宛に送るだけ。
- WiFiインフラ(ルーター、hostname解決等)は既に構築済み・動作確認済み。CH9329やMAX3421のような外付けチップ・配線は一切不要。
- Bluetoothよりも実装コストが低い(後述)。

つまり要件にあった「esp32-kvm-ipに直接(かBluetooth)モード(slave)みたいなのを設ける?」に対する回答は、**新規のslaveモードを設ける必要すらなく、今のDevice側は"WiFiで待ち受けるUDPサーバー"として既に完成している**、ということ。Host側だけ新規実装すればいい。

#### 出力方式(route)の比較

| 方式 | 追加ハード | 実装コスト | 備考 |
|---|---|---|---|
| **WiFi→既存esp32-kvm-ip(Device)** | なし | 低(Host側送信ロジックのみ) | 受信側は無改造。まずはこれ一択 |
| UART→CH9329 | CH9329モジュール要購入・配線 | 中(CH9329独自シリアルプロトコルの実装が要る) | Target PC側は本当にただのUSB HIDとして見える。1筐体に収めたい場合の将来案 |
| SPI/UART→MAX3421経由でDevice側を自作 | MAX3421モジュール要購入・配線 | 高(MAX3421自体はHostコントローラなので、今回は不要。Device化するなら別途USBデバイスコントローラが要る) | 今回の用途とは逆方向(MAX3421はHost用)なので基本不採用 |
| BLE HID (HOGP) でTarget PCに直接ペア接続 | なし(ESP32-S3は BLEのみ、Classic BTは非対応) | 中〜高(NimBLE HIDプロファイルの実装が要る。今のTinyUSB Device実装とは別のスタック) | 配線もWiFiも不要になる利点はあるが、初回実装としては優先度低。将来Target側にWiFi/USBどちらも使えない状況(タブレット等)向けの拡張候補 |

→ まずは表の1番目(WiFi再利用)で実装し、動いてから必要に応じてCH9329配線やBLE HID出力を追加する、という段階案を推奨。

#### USB Host側の技術詳細
- ESP-IDFのUSB Hostライブラリ(`usb_host`コンポーネント、IDF v5.x)は**Hub経由の複数デバイス接続を標準でサポート**している(Hub自体もUSB Hostライブラリが内部で扱う)。要件にあった「Hub接続もありうる複数のUSB機器」は、こちらでほぼ実装済みの機能に乗るだけで対応可能 — 自分でHubプロトコルを書く必要はない。
- HIDクラスドライバ(公式サンプル `examples/peripherals/usb/host/hid` 、コンポーネント名や関数シグネチャの詳細は実装時に要確認)は、接続されたデバイスがBoot Protocolに対応していれば、**すでにパース済みのキーボード/マウス構造体**(今のDevice側`hid_task.c`が使っているのと同じ`hid_keyboard_report_t`/`hid_mouse_report_t`相当のBootフォーマット)をコールバックで渡してくれる。市販キーボード/マウスはBIOS互換のためほぼ全てBoot Protocolに対応しているので、**MVPでは汎用HID Report Descriptorパーサーを自前で書かなくてよい可能性が高い** — これがUSBホスト実装で一番面倒な部分なので、コスト面で大きい。
- Report Protocolでしか動かない特殊デバイス(高DPIゲーミングマウス等)への対応は、Boot Protocolで一旦動くものを作ってから後回しでよい。

#### filter/conv実装方針(.hへのルール直書き)
方針通り、コンパイル時定数のルールテーブルが最小コスト。イメージ:

```c
// filter_rules.h
typedef enum { RULE_PASSTHROUGH, RULE_DROP, RULE_REMAP_TO_KEY } rule_action_t;

typedef struct {
    uint8_t       src_type;   // SRC_MOUSE_BUTTON / SRC_MOUSE_WHEEL / SRC_KEY 等
    uint16_t      src_code;   // 元のUsage/ビット
    rule_action_t action;
    uint16_t      dst_code;   // REMAPの場合の出力HIDコード
    uint8_t       dst_mods;   // REMAPの場合の出力モディファイア
} filter_rule_t;

static const filter_rule_t FILTER_RULES[] = {
    { SRC_MOUSE_WHEEL,  0,             RULE_DROP,         0,               0        },
    { SRC_MOUSE_BUTTON, MOUSE_BACK,    RULE_REMAP_TO_KEY, HID_KEY_ARROW_L, MOD_ALT  },
    { SRC_MOUSE_BUTTON, MOUSE_FORWARD, RULE_REMAP_TO_KEY, HID_KEY_ARROW_R, MOD_ALT  },
};
```

Host側でBoot Protocol構造体を受け取った直後(=`protocol.h`にパックする直前)にこのテーブルを線形サーチして適用すればいい。件数が増えたらハッシュテーブル化等を検討すればよく、今の規模なら線形サーチで十分。

#### 同一リポジトリでのHost/Device切り替え
ESP32-S3のネイティブUSBペリフェラルは**Host/Deviceの同時利用は不可**(排他)なので、1枚のボードが同時に両方にはなれない。ただし「同じソースツリー・ビルド時に役割を選ぶ」ことは問題なく可能:

- `Kconfig.projbuild`に`CONFIG_KVM_ROLE_HOST` / `CONFIG_KVM_ROLE_DEVICE`のchoiceを追加
- 共通で使い回せるもの: `wifi_manager.c/h`, `protocol.h`, `status_led.c/h`, `wifi_credentials.h`
- Device側専用: `usb_descriptors.c/h`, `hid_task.c/h`(既存のまま)
- Host側専用(新規): `usb_host_task.c/h`(USB Hostライブラリ初期化・HIDクラスドライバ登録), `filter_rules.h`
- `main/CMakeLists.txt`の`SRCS`をKconfigの値で条件分岐(`if(CONFIG_KVM_ROLE_HOST) ... else() ...`)

これで「モード切り替えでHostにもDeviceにもなる」という要望は、**同一リポジトリ・同一menuconfigフロー**の中でビルド時選択として実現できる(ただし1枚のボードは書き込み時にどちらか一方の役割に固定される — 実行時トグルではない)。

#### 次のステップ案(実装する場合)
1. 公式サンプル`examples/peripherals/usb/host/hid`を土台に、`esp32-kvm-ip`内に`CONFIG_KVM_ROLE_HOST`ビルド構成を追加
2. HIDホストのBoot Protocolコールバックを受けて`filter_rules.h`を適用し、`protocol.h`の`udp_packet_t`に詰めて既存Device機のIP宛にUDP送信するだけの薄い`usb_host_task.c`を書く
3. 既存のDevice側ボード1台に向けて実機テスト(Host用ボードはもう1枚のESP32-S3が必要)
4. 動作確認後、必要ならCH9329配線やBLE HID出力を追加検討

### 決定: role切り替えはKconfigの`choice`ではなくビルドディレクトリ分割
上の「同一リポジトリでのHost/Device切り替え」案について、実際に試すと`idf.py menuconfig`のWIFI_SSID/PASSWORDの件と同じ理由(`sdkconfig.h`が変わるとほぼ全ファイル再コンパイル)でrole切り替えのたびに大幅リビルドが発生することが判明。そこで方針を修正:

- role選択はKconfigの`choice`にせず、**ビルドディレクトリを役割ごとに分ける**(`idf.py -B build.host`/`-B build.device`)。ninja/ccacheの状態がディレクトリごとに独立するので、切り替えコストはゼロ(それぞれのディレクトリで差分ビルドが効く)。
- `main/CMakeLists.txt`の`SRCS`/`PRIV_REQUIRES`はCMakeの`-D`変数(`KVM_ROLE=HOST`/`DEVICE`)で分岐。`sdkconfig.h`には触れないので他コンポーネントの再コンパイルは誘発しない。
- 切り替え・ビルド操作は`Wireless_USBHID/bin/`配下にラッパースクリプト(`build_host.sh`/`build_device.sh`)を用意し、毎回`-B build.xxx -D KVM_ROLE=XXX`を打たなくて済むようにする。

### 実装完了・実機ビルド確認済み
上記方針でMVPを実装し、この環境に偶然`/opt/esp-idf5.5.1`が入っていたので**実際にidf.pyでビルドして動作確認できた**(コンパイルが通ることの確認までで、実機flash/実際のHIDデバイス接続テストはまだ)。

- `main/CMakeLists.txt`: `KVM_ROLE`(未指定時は`DEVICE`)でSRCS/PRIV_REQUIRESを分岐
- `main/main_host.c` / `main/usb_host_task.c` / `main/usb_host_task.h`: Host role本体。公式サンプル`examples/peripherals/usb/host/hid`(コンポーネント`espressif/usb_host_hid` v1.2.0)を土台に、Boot ProtocolのキーボードHID/マウスHIDレポートを`filter_rules.h`経由でフィルタし、`protocol.h`の`udp_packet_t`にそのまま詰めて`KVM_TARGET_HOST`宛にUDP送信するだけの薄い実装
- `main/filter_rules.h`: フィルタ/変換フック(`filter_keyboard_report()`/`filter_mouse_report()`)。初期状態は素通し(true, 中身無加工)。Boot Protocolのマウスは button1-3 + X/Y のみでホイール非対応(仕様通り。ホイールが要るならReport Protocolディスクリプタ解析が別途必要 - 今回は未実装)
- `main/wifi_credentials.h(.example)`: `KVM_TARGET_HOST`(Device機のIP/ホスト名)を追加
- `main/idf_component.yml`: `espressif/usb_host_hid`を追加(マニフェスト経由の依存は常にmainのREQUIRESに入るため、Device roleでも常にコンパイルはされる。ただし何も呼ばないので実害なし)
- `sdkconfig.defaults`: `CONFIG_USB_HOST_HUBS_SUPPORTED=y`を追加(Hub経由の複数デバイス接続に対応)
- `bin/build_host.sh` / `bin/build_device.sh`: それぞれ`build.host/`(新規) / `build/`(既存デフォルト、変更なし)を使うラッパー

**ビルド確認結果**:
- Host role (`bin/build_host.sh build`): warning/error 0件、初回一発で成功。バイナリサイズ 0xcc3c0 bytes(1MBパーティションの20%空き)
- Device role (`bin/build_device.sh build`): 既存の`build/`ディレクトリで再ビルドしても warning/error 0件、既存コンポーネントは再コンパイルされず(main配下の変更ファイルのみ差分ビルド)、退行なし確認済み。バイナリサイズ 0xc3980 bytes(24%空き)
- 想定通り、role切り替え(Host↔Device)でも他コンポーネントの巻き添え再ビルドは発生しなかった

- Hub経由の複数デバイス接続
- Device機への実際のUDP到達・HID出力
- `KVM_TARGET_HOST`は現状プレースホルダ値のまま(`wifi_credentials.h`の実物は要編集)

### 注意: Host roleはVBUS給電が要る(ハード制約、ソフトでは解決不可)
Device roleはTarget PCから給電される側だが、Host roleは逆にキーボード/マウス側へ5V(VBUS)を供給する側になる。**XIAO ESP32S3は素の状態だとHost給電用のboost/power-switch回路を持っておらず**(Seeed公式フォーラムで確認済み)、USB-Cポートに挿したキーボード/マウスがそもそも認識されない(ソフトの問題ではない)。

- 回避策: VBUSピン(Pin 14, J1 Pin7 - USB-CコネクタのVBUSネットに直結)へ外部から5Vを注入する
- 参考: Espressif公式`ESP32-S3-USB-OTG`ボードは最初からこの機構(boost converter + power switch IC、GPIOで`BOOST_EN`/`DEV_VBUS_EN`切り替え)を持っている
- ソフト側(`usb_host_task.c`等)はどちらの電源構成でも変更不要

### 修正: Host/DeviceでWIFI_HOSTNAME衝突していたバグ
`wifi_credentials.h`はHost/Device共有の1ファイルなので、`WIFI_HOSTNAME`(DHCPホスト名)が両roleで同じ値になっていた。IP自体はMACベースなので衝突しないが、OpenWRTのリース一覧で2台とも同じ名前になり見分けがつかない(そもそもこの機能を入れた目的が見分けるためだったので本末転倒)。`main_host.c`側のみ`WIFI_HOSTNAME "-host"`(文字列リテラル連結)にして解消。Device roleは無変更。ビルド確認済み。
