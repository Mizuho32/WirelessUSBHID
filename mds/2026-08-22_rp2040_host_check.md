# RP2040でこのワイヤレスドングルが7バイート届くか確認

`mds/2026-08-22_wireless_dongle_short_reports.md`で調査してきた9ボタンマウス(Maxxterワイヤレスレシーバー、248a:8579)の3バイート切り詰め問題について、ESP32-S3側の要求内容(SET_PROTOCOL等)ではなくホストコントローラ自体(あるいはESP-IDFの`usb_host_hid`ドライバというソフトウェア層)固有の問題である可能性が浮上した。安いMCUのUSBホストなら他でも同じ問題が起きるのか、それともESP32(かそのドライバ)固有なのかを切り分けるため、別のMCU(RP2040、ESP32-S3とは全く別のホストコントローラ・別のソフトウェアスタック=TinyUSB)で同じドングルを試す。

## 目的
- 同じマウスをRP2040に挿して、Report Protocol(7バイート、ホイール込み)がちゃんと届くかだけをまず確認する。
- 届けば「ESP32(かesp-idfの`usb_host_hid`ドライバ)固有の問題」と分かり、ESP32側をソフトウェアで直す価値があると判断できる。
- 届かなければ「安価なMCUのUSBホスト実装全般の限界」に近い話になり、この方向のマウス対応は諦めてよさそうという判断材料になる。

## ハードウェア構成
- 秋月のRP2040互換ボード。回路図で確認済み: D+/D-がRP2040のネイティブUSB(USB_DP/USB_DM)ピンに直結。
- ESP32の時と同じく、VBUS相当の外部電源 + 既設のType-CホストコネクタでMaxxterドングルを接続。

## 環境
- Arduino IDE v2(既存のセットアップをそのまま使用)
- arduino-pico core 5.7.0(インストール済み、`~/.arduino15/packages/rp2040/hardware/rp2040/5.7.0/`)
- 同梱の`Adafruit_TinyUSB_Arduino`ライブラリ(TinyUSBのHost HID API - `tuh_hid_*` - をラップしたもの)
- **Tools → USB Stack → "Adafruit TinyUSB Host (native)"** を選択すること(`USE_TINYUSB_HOST`が定義される。これが無いとビルドエラーになる)

### 重要な制約: デバッグ出力はSerial1(UART)経由
RP2040はネイティブUSBペリフェラルが1個しかない。今回それをHost用途に使うので、同じポートでUSB-CDC(Arduinoの`Serial`)は使えない。デバッグ出力は`Serial1`(ハードウェアUART、通常GP0=TX/GP1=RX)経由で行い、USB-シリアル変換器かFTDIケーブル等で見る必要がある(Adafruit公式の`host_device_info`サンプルも同じ理由でSerial1を使っている)。

## スケッチ
`rp2040_host_check/rp2040_host_check.ino`

`Adafruit_TinyUSB_Arduino/src/class/hid/hid_host.h`の生TinyUSB Host HID API(`tuh_hid_mount_cb` / `tuh_hid_report_received_cb`)をそのまま使い、ESP32側の調査でやったのと同じ形で:
- マウント時にReport Descriptorをまるごとhexダンプ(ESP32側で確認済みの148バイート記述子と一致するはず)
- 以降届く生レポートを、都度そのままバイト長+hexでダンプ

TinyUSBは`CFG_TUH_HID_SET_PROTOCOL_ON_ENUM=1`がデフォルトで、かつ既定のプロトコルは`HID_PROTOCOL_BOOT`(ライブラリ側のコメントより)。今回はESP32側と同じ土俵で比較したいので、`setup()`で明示的に`tuh_hid_set_default_protocol(HID_PROTOCOL_REPORT)`を呼び、Report Protocolを要求させている。

## 結果: RP2040では7バイート丸ごと正しく届く — ESP32固有の問題と確定

いくつかハマったポイントを乗り越えて実機確認できた:

### ハマった点1: ボード上のUSBポートがそもそもHostとして給電できない
基板の回路図を見ると、コネクタのVBUSピンから基板の5Vレールへ、アノードがUSB側を向いたショットキーダイオードが入っている——つまり「USBから電源をもらってボードを動かす(デバイスモード)」専用の電源経路で、逆方向(ボード→VBUSへ給電)はダイオードに塞がれていて構造的に不可能。GP2040-CE等のRP2040 USB Host改造でも定番の制約。今回は**VBUSピンに5Vをジャンパー線で直結**して回避(ダイオードのバイパス/専用ロードスイッチ追加が正攻法だが、確認だけならこれで十分)。

### ハマった点2: ビルド環境の食い違い(rp2040コアのバージョン、ボード種別)
Windows Arduino IDE 2では動くのに、Linux側の`arduino-cli`ビルドではUSB列挙すら起きない(BOOTSELモードは反応するのでハード自体は無事)という謎現象が発生。原因を切り分けていく過程で:
- rp2040コアのバージョンがLinux側は5.7.0、Windows側は6.0.0で食い違っていた(`arduino-cli`が参照する設定ファイルにEarle Philhowerのボードマネージャ追加URLが登録されてなかったのが原因、`~/.arduinoIDE/arduino-cli.yaml`を明示的に指定して解決)
- ボード種別も「Generic RP2040」と「Raspberry Pi Pico」で試していて、最終的に「Raspberry Pi Pico」で実機が起動することを確認
- さらに`--export-binaries`で書き出した`.uf2`が、同じソース・同じFQBNでビルドしたはずの内部キャッシュ(`~/.cache/arduino/sketches/.../`)の`.uf2`と実機上で違う挙動を示すケースが一度あった(原因未特定、プロジェクトディレクトリがNFSマウントなのが関係してる可能性)。`--build-path`で最初から`/tmp`に直接ビルドする方式(`bin/build_flash_rp2040.sh`)に切り替えて解消。

### 実機確認結果
`rp2040_host_check.ino`をRaspberry Pi Picoボード設定・Adafruit TinyUSB Host (native)で書き込み、Maxxterドングルを接続:

```
[1:0] raw report (7 bytes): 01 00 00 00 00 00 00   # アイドル
[1:0] raw report (7 bytes): 01 00 00 00 00 00 01   # ホイール上
[1:0] raw report (7 bytes): 01 00 00 00 00 00 ff   # ホイール下
```

`data/usbhid-dump.txt`(実PCでの`usbhid-dump`キャプチャ)の値と完全に一致 — Report ID込み・7バイート丸ごと、ホイールも符号付きでちゃんと乗っている。**ESP32では一度も観測できなかった形が、RP2040(TinyUSB Hostスタック)では最初から普通に届く。**

### 結論
このドングルの3バイート切り詰め問題は、**ドングル自体のファームウェアの問題でも、「安価なMCU全般のUSBホストの限界」でもなく、ESP32-S3のUSBホストコントローラか`espressif/usb_host_hid`ドライバ(ESP-IDF側のソフトウェアスタック)に固有の問題**だったと確定した。RP2040+TinyUSBという全く別のホストコントローラ・別のソフトウェアスタックでは何の工夫もなく素直に動く。

ESP32側でこれ以上ソフトウェア的に追うなら、`espressif/usb_host_hid`(または更に低レベルの`usb_host`)のIssueとして報告する、あるいはESP-IDFのバージョン更新を待つ、といった方向性になりそうだが、これは別途判断。
