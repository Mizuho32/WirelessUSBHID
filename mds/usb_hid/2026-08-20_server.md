## server.pyをLinuxでも

server.pyをLinuxでも動くようにしたい。
オリジナル実装だと、scroll lockでHost/Targetの切り替えやるみたいだけど、これLinux(Wayland Plasma)でも可能?

## 調査結果

### 結論: Wayland(KDE Plasma)でも可能。ただし実装方式はWindows版と別物になる

現状の`server.py`はWindows専用のWinAPI(`WH_KEYBOARD_LL`/`WH_MOUSE_LL`のグローバルフック + Raw Input)に依存しており、これをそのままLinuxに移植することはできない。Linux版は**evdev(`/dev/input/eventX`)を直接読む方式**で作り直すのが妥当。

### 現状のWindows実装の仕組み(移植の基準として整理)

- `winapi_hooks.py`: `SetWindowsHookExW(WH_KEYBOARD_LL/WH_MOUSE_LL, ...)`でOS全体のキーボード/マウスイベントを最初に横取りするコールバックを登録。KVM ON中はコールバックが`1`を返すことでOS/他アプリへのイベント伝播を止める(＝Host PC側では何も起きない)。Scroll Lockキー自体は常にフックプロシージャに届くので、KVM ON/OFFのトグルとして使える。
- マウス移動量はOSのポインタ加速の影響を受けない`Raw Input`(`WM_INPUT`)から取得(1:1のセンサー値)。

### Linux(X11/Wayland問わず)での等価な仕組み: evdev + `EVIOCGRAB`

- Linuxのカーネル入力サブシステム`evdev`(`/dev/input/eventX`)は、X11やWaylandといった上位のディスプレイサーバーより**下のレイヤー**にあるため、X11/Waylandのどちらであっても、またKDE PlasmaでもGNOMEでも同じ仕組みが使える。Wayland特有の制約は関係ない。
- Pythonの`python-evdev`ライブラリで`InputDevice("/dev/input/eventX")`を開き、`read_loop()`で全イベントを監視できる。これはWinAPIのフックコールバックとほぼ同じ役割。
- イベントの**伝播ブロック**は`EVIOCGRAB`ioctl(`python-evdev`では`device.grab()`)で行う。これはそのデバイスを排他的に掴み、他の消費者(X11のドライバ、libinput、Waylandコンポジタ)には一切イベントが渡らなくなる仕組み。WinAPIフックが`1`を返してイベントを握りつぶすのと同じ効果になる。
  - 自分のプロセスは`grab()`中でも引き続きイベントを読めるので、「Scroll Lockだけは常に監視してトグルに使う」という現状のロジックもそのまま踏襲できる。
  - 参考: [python-evdev API Reference](https://python-evdev.readthedocs.io/en/latest/apidoc.html)、[exclusive-keyboard-access (EVIOCGRABの使用例)](https://github.com/whizse/exclusive-keyboard-access)
- マウスの生の相対移動量(`REL_X`/`REL_Y`)もevdevならOS/DEのポインタ加速が適用される**前**のカーネルレベルの値なので、Windows版のRaw Inputと同等かそれ以上に単純に取れる。
- 注意点:
  - `/dev/input/eventX`への読み取りには通常root権限か`input`グループへの所属(+ udevのパーミッション設定)が必要。
  - 物理キーボード1台でも複数の`eventX`ノード(通常キー用、メディアキー用など)に分かれていることがあるため、該当デバイスを列挙して必要なものを全て`grab()`する必要がある。

### もう一つの選択肢: `org.freedesktop.portal.InputCapture`(Wayland公式のサンドボックス対応ルート)

- Barrier/Synergyの後継である[Deskflow](https://github.com/deskflow/deskflow)や[input-leap](https://github.com/input-leap/input-leap)は、Wayland上ではこの`InputCapture`ポータル(xdg-desktop-portal 1.18で追加、`libei`/EISプロトコル経由)を使ってちょうど今回のような「ローカル入力を捕捉してリモートに転送する」動作を実現している。
- KWin(KDE Plasma)側の対応は**Plasma 6.1で導入済み**([KWin MR #5496](https://invent.kde.org/plasma/kwin/-/merge_requests/5496)、[xdg-desktop-portal-kde Issue #12](https://invent.kde.org/plasma/xdg-desktop-portal-kde/-/issues/12))。ただしまだ枯れきっていない面もあり、実際に[Plasma 6.1でEIS接続に失敗する不具合報告](https://github.com/input-leap/input-leap/issues/1908)も見つかった。
- こちらは非特権(サンドボックス内でも動く)でWaylandの流儀に沿った「正式な」方法だが、D-Bus経由のポータル交渉 + 独自バイナリプロトコル(EIS)の実装が必要で、evdev方式に比べて実装コストがかなり高い。今回の規模の個人開発では過剰投資になる可能性が高い。

### 推奨

evdev + `EVIOCGRAB`方式で実装するのが妥当。Windows版の`winapi_hooks.py`と同じ構造(常時イベント監視 → Scroll Lockでトグル → grab状態で伝播をON/OFF)にほぼそのまま対応付けられ、X11/Wayland/DEを問わず動く。`input`グループへの追加が事前セットアップとして必要になる旨はREADMEに明記が必要。

## 実装方針

- **キーボードのみ先行実装、マウスは対象外**(前回の相談通り、マウスはボタン/移動量/ホイールとイベント種別が増えて面倒なので後回し)。マウス関連の状態(`state.mouse_*`)は一切触らないため、UDP側もマウスパケットは送信されず、Host PC側のマウスは常時そのまま動く。
- **`server.py`はWindows版を無改造で維持**。`winapi_hooks.py`の`InputHookManager`クラスは`__init__(state)` / `start()` / `stop()` / `process_messages()`という最小インターフェースなので、Linux版として同じインターフェースを持つ`evdev_hooks.py`を新設し、`server.py`側は`platform.system()`で読み込むモジュールを切り替えるだけにする(分岐は数行で済む)。
- **ブロック方式**: `python-evdev`で`/dev/input/eventX`を非grab状態で開き、`selectors`で複数デバイスを多重化しつつ常時監視(WinAPIのフックコールバックに相当)。Scroll Lockキーが来たら`kvm_active`をトグルし、そのタイミングで対象デバイスに対して`device.grab()`/`ungrab()`を呼ぶ。`grab()`中も自プロセスへのイベント配信は続く(他プロセスへの伝播だけが止まる)ので、Scroll Lockの監視自体はgrab状態に関わらず継続できる。
- **対象デバイスの自動検出**: `EV_REL`/`EV_ABS`を持つデバイス(マウス・タッチパッド類)は除外し、`EV_KEY`を持つデバイスのみを対象にする。これで物理キーボード本体に加えて、メディアキーが別ノードに分かれている場合もまとめて拾える。
- **キーコード対応表**: `hid_keymap.py`(Windows VK_*→HID)と同じHIDターゲットになるよう`evdev_keymap.py`を新設。値は`/usr/include/linux/input-event-codes.h`の実物から確認して作成(記憶だけに頼らず実ファイルで裏取り)。JIS/Koreanの国際キーはLinux側の方がコード粒度が細かく、Windows版より正確に割り当てられた。
- 事前セットアップとして`input`グループへの追加(`sudo usermod -aG input $USER`)が必要な旨をREADMEに追記する。
