# RP2040側 dormant sleep 対応プラン

[2026-8-30_Sleep.md](2026-8-30_Sleep.md)の続き。ESP32側のPCサスペンド検知・WiFi停止は実装・実機確認済み。ここでは、RP2040ブリッジ側(`usb_host_rp2040_bridge.c`/`rp2040_host_bridge.ino`)も連動してdormant sleepさせるプランをまとめる。**未実装、設計のみ**。

## スコープ

- HID操作(マウス/キーボード操作)そのものをwakeトリガに使う案は諦める(dormant中はUSB PHYのクロックが止まりD+/D-のライン状態を検知できないため - 2026-8-30_Sleep.md参照)。
- 代わりに、ESP32側が既に検知しているPCのUSBサスペンド/レジューム(`tud_suspend_cb`/`tud_resume_cb`)をトリガに、ESP32からRP2040へUART経由でsleep/wakeを指示する方式にする。
- 対象はKVM_ROLE=HOST + RP2040ブリッジbackend使用時のみ。

## 現状の確認事項

- **現行のブリッジUARTプロトコルはRP2040→ESP32の一方向のみ**。RP2040側(`rp2040_host_bridge.ino`)はどこにも`Serial1.available()`/`Serial1.read()`を呼んでおらず、受信処理が一切無い。ESP32→RP2040へコマンドを送る経路は新規に実装する必要がある。
- 配線: ESP32側 GPIO9(TX)/GPIO8(RX)、`UART_NUM_1`、460800bps(`usb_host_rp2040_bridge.c`)。RP2040側 GP0(TX)/GP1(RX)、`Serial1`(hardware UART0)、同じく460800bps(`rp2040_host_bridge.ino`)。ESP32 TX(GPIO9)→RP2040 RX(GP1)、RP2040 TX(GP0)→ESP32 RX(GPIO8)のクロス配線。
- RP2040のdormant sleepにはUART専用のwakeソースは無く、GPIOレベル/エッジのみ(`gpio_set_dormant_irq_enabled()`)。UART機能とGPIO機能は同じピンのfuncsel切り替えで両立できるので、追加配線は不要 - dormant前にRXピンをGPIO入力へ切り替えてedge-wakeを武装し、起床後にUART機能へ戻す。
- ESP32-S3側もUARTはGPIO Matrix経由でピンにマッピングされているので、同様にfuncsel切替は可能。ただし今回はESP32側のUARTペリフェラルは動かしっぱなしで良さそうと判断(下記「wake」参照) - ESP32はUART idle時に自然とHIGHを維持するので、わざわざGPIOに切り替えて明示的にHIGHを保持する必要が無い。

## 設計案

### 1. 新規メッセージタイプ(ESP32→RP2040方向)
既存のフレーム構造(`[0xAA sync][msg_type][dev_addr][idx][itf_protocol][len_lo][len_hi][payload...][checksum]`、`usb_host_rp2040_bridge.c`)を流用し、方向を逆にする形で、ESP32→RP2040向けの新しいmsg_typeを追加する(例: `BRIDGE_CMD_SLEEP`)。

明示的な`BRIDGE_CMD_WAKE`は不要な可能性が高い: sleep中RP2040はUARTを読めない(GPIO edge-wakeでしか気づけない)ので、コマンドとして送る意味がなく、「何かバイトを送る」こと自体がUART start bitのfalling edgeとしてwakeトリガになる。既存のハートビート/次のフレーム送信がそのままwake信号を兼ねる。

### 2. RP2040側の受信処理を新規実装
現状Serial1の受信処理が皆無なので、ゼロから追加が必要:
- メインループで`Serial1.available()`をチェックし、sync byte + `BRIDGE_CMD_SLEEP`を受信したら:
  1. 送信中のフレームがあれば完了させる
  2. `Serial1.end()`でUART0を止める
  3. GP1(RX)を`gpio_set_function(1, GPIO_FUNC_SIO)`でGPIO入力に変更
  4. `gpio_set_dormant_irq_enabled(1, GPIO_IRQ_EDGE_FALL, true)`でdormant wakeを武装(UART idle=HIGH、start bit=fallなので立ち下がりエッジ)
  5. dormantへ突入(pico-extrasの`sleep_run_from_dormant_source()`等)

### 3. wake(復帰)
- ESP32側: `power_manager.c`がPC resumeを検知したら(既存の`tud_resume_cb`経由)、RP2040ブリッジがアクティブな場合、UARTで1バイト送るだけ(次のハートビート/フレームで自然に発生)でRP2040のRXピンにfalling edgeが起き、dormant wakeがトリガされる想定。
  - フォールバック案(先に単純なバイト送信だけで試して、不十分ならこちらを追加): 460800bpsのUART start bitは約2.17usしかなく、dormant wake回路がより長いパルスを要求する場合に備え、GPIO9を一時的にGPIO出力へ切り替えて数百us〜数ms明示的にLOWを保持してから、UART機能に戻して通常送信する。
- RP2040側: wake後、GP1を`gpio_set_function(1, GPIO_FUNC_UART)`に戻し、`Serial1.begin(460800)`で再初期化。起床直後の数バイトは失われる前提(既存の同期バイト方式で自己回復する想定、未検証)。

### 4. ESP32側(power_manager.c)との統合
現在の`power_manager_task`はPC suspend/resume検知でWiFi停止/再開・LED連動を行っている(Host role含む)。ここに「RP2040ブリッジがアクティブな場合、RP2040へSLEEPコマンドを送る」処理を追加する形が自然。

## 未決定・要相談

- ESP32→RP2040コマンドの正確なmsg_type番号・フレーム仕様
- 有効/無効の制御を、既存の`usb_suspend_wifi_sleep`mrubyトグルに乗せるか、別トグル(例: `usb_suspend_rp2040_sleep`)を新設するか - RP2040側は再列挙遅延という別のリスクを背負うので、分けた方が安全かもしれない
- wakeのGPIO手動パルスのフォールバックを最初から入れるか、まず単純なUARTバイト送信だけで試すか

## 未検証

- RP2040がUSB Hostとして自分がVBUS/SOFを供給している側なので、dormant化で接続デバイス(マウス/キーボード)から見て切断扱いになり、復帰後は再列挙が必要になる可能性が高い。遅延がどの程度になるかは接続機器依存で未実測。
- 460800bpsでのUART start bit(約2.17us)がdormant wakeのエッジ検出として確実に機能するか(パルス幅要件)
- 起床直後の数バイト欠落を既存の同期バイト方式が実際に吸収できるか
