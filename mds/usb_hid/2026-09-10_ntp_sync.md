# 起動時のNTP時刻合わせ

`mruby`の`Time.now`がEpoch(起動からの経過時間相当、実際の日付ではない)を返すことに気づいたことがきっかけ。ESP32-S3にはバッテリーバックアップ付きRTCが無いため、起動のたびに内部時計は0からカウントを始める - `Time.now`に限らずシステム全体が「本当の日時」を知らない状態になっている。

## 対応

ESP-IDFの`esp_netif_sntp`(標準機能、追加コンポーネント不要 - `esp_netif`はHost/Device両ロールとも元々`PRIV_REQUIRES`済み)でSNTPクライアントを起動する。

- **起動場所**: `wifi_manager.c`の`IP_EVENT_STA_GOT_IP`(WiFi初回接続成功時、Host/Device両ロール共通)。`s_ntp_started`で一度だけ初期化(再接続のたびに呼び直す必要は無い - `esp_netif_sntp`自身が背後で定期的に再同期し続ける、デフォルト1時間間隔)。
- **サーバ**: スクリプトが`ntp_sync "<server>"`で渡した文字列(例: `"pool.ntp.org"`)。固定値のハードコードはしていない。
- **タイムゾーン**: 別途`timezone "..."`で対応(下記)。

## デフォルトOFF、サーバ名を渡すと有効化(いつものパターンから変更)

最初は`ntp_sync false`という真偽値トグル(デフォルトtrue)で実装したが、「Time使わないスクリプトもあるんだし、デフォルトOFFでサーバー名指定で有効化の方が素直」というフィードバックを受けて設計変更した:

- `ntp_sync "pool.ntp.org"`のように**サーバー名の文字列を渡すこと自体が有効化**(`hostname "..."`と同じ、文字列引数+`_set`フラグのパターン - 独立した真偽値の概念を持たない)
- デフォルトは**無効**(スクリプトが一度も呼ばなければ`NULL`、SNTP自体を起動しない) - `wifi_fast_reconnect_static_ip`と同じ「安全側はOFF」の考え方に合わせた
- `wifi_manager.c`は両ロール共通なので、Device role(mruby無し)ではweak symbol経由で常に無効(そもそもスクリプトが無くサーバー名を指定しようが無いので、Host roleのように「有効はできるがデフォルト無効」ではなく「常に無効」)

## タイムゾーン: `timezone "JST-9"`

NTP同期しても`Time.now`が返すのはUTC。輪をかけて、mrubyの`Time#localtime`は**引数を取らない**(`components/mruby/mruby/mrbgems/mruby-time/src/time.c`で`MRB_ARGS_NONE()`固定 - MRIの`Time#localtime(utc_offset=nil)`と違いオフセットを渡す口が無い)実装で、中身は単に libc の`localtime_r()`を呼ぶだけ。つまり`TZ`が設定されてなければ`localtime`は`gmtime`と全く同じ(UTC)にしかならず、「事実上動かない」状態だった。

`timezone "JST-9"`(`setenv("TZ", ..., 1); tzset();`をスクリプト読み込み時に即実行 - NTPと違いネットワーク非依存なのでWiFi接続を待つ理由が無い)で対応。デフォルトは未設定(UTCのまま)。

### 書式: POSIX `TZ`環境変数(独自フォーマットではない)

newlib(ESP-IDFのCライブラリ)の`tzset()`が解釈する、**POSIX(IEEE Std 1003.1)で標準化された`TZ`変数の書式**。調べるなら「POSIX TZ variable format」「glibc TZ variable」で検索(`man tzset`、glibcマニュアルの"TZ Variable"章が定番)。IANA名(`Asia/Tokyo`等)はzoneinfoデータベースが要るため、ESP32上のnewlibでは使えない(固定オフセット/DST規則を直接書く形式のみ)。

```
std offset [dst [offset] [,rule]]
```

- `std`/`dst`: 任意の名前(表示用ラベルに過ぎず、検索されるわけではない)
- `offset`: **地方時からUTCを引くと合う数 - 符号が直感と逆**(日本はUTC+9だが`JST-9`と書く: UTC = 地方時 − 9)。一番のハマりどころ
- `,rule`: サマータイムの開始/終了規則(`M<月>.<週>.<曜日>`形式が主流)

| 地域 | TZ文字列 |
|---|---|
| 日本(UTC+9、DST無し) | `JST-9` |
| UTC固定 | `UTC0` |
| 米国東部(DST有り) | `EST5EDT,M3.2.0,M11.1.0/2` |
| 米国太平洋(DST有り) | `PST8PDT,M3.2.0,M11.1.0/2` |
| 中央ヨーロッパ(DST有り) | `CET-1CEST,M3.5.0,M10.5.0/3` |
| インド(UTC+5:30、DST無し) | `IST-5:30` |

固定オフセット(`JST-9`等)はESP-IDF自身のテストコード(`esp_libc`の`test_time.c`、`setenv("TZ", "UTC+0", 1)`)でも使われてる標準パターンで確実。`,rule`付きのDST規則は同じnewlib標準実装が解釈するはずだが、この環境では未検証。

## 実機ビルド確認

Host/Device両ロールともビルド成功、Flash使用率は変化なし(Host 25%空き、Device 73〜74%空き)。`ntp_sync`実装後(`timezone`追加前)にWebUI経由のWiFi OTA(`bin/upload_firmware.py`)で実機フラッシュ済み - OTA機能自体の実機初動作確認も兼ねた。`Time.now`が実際の日付を返すこと自体の確認、および`timezone`の実機確認は未検証。
