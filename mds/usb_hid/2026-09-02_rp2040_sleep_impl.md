# RP2040側 dormant sleep 実装

設計は[[2026-08-31_rp2040_sleep_plan]]参照。このドキュメントは実際に実装した内容、設計からの変更点、ビルドで踏んだ落とし穴の記録。**実機確認済み**(消費電力: 通常時 約1W → ESP32側WiFiサスペンドのみで約0.8W → 本機能も有効化して約0.56W)。

## 実装済み

### ブリッジプロトコル(双方向化)

- 既存のRP2040→ESP32一方向フレーム(`[0xAA sync][msg_type]...`)に、ESP32→RP2040方向の新規msg_typeを追加: `BRIDGE_CMD_SLEEP = 0x06`、`BRIDGE_CMD_WAKE = 0x07`(両方とも`usb_host_rp2040_bridge.c`・`rp2040_host_bridge.ino`双方の`#define`を手で一致させる必要がある、既存の他msg_typeと同じ運用)
- `BRIDGE_CMD_WAKE`は実質「中身に意味がない」フレーム: dormant中のRP2040はUARTを読めないので、コマンドとしてパースされて初めて意味を持つわけではなく、**バイト列がRXピンに流れること自体(UART start bitの立ち下がりエッジ)がdormant wakeの物理トリガ**になる。それでも明示的なmsg_typeとして送っているのは、RP2040側の再同期後ログで「ちゃんと復帰後の通信が生きてる」ことを確認できるようにするため

### ESP32側(`usb_host_rp2040_bridge.c`/`.h`)

- `usb_host_rp2040_bridge_send_sleep()`/`_send_wake()`: ゼロペイロードのコマンドフレームを送信(`bridge_send_cmd()`、チェックサムは`msg_type`単体に簡略化される)
- `usb_host_rp2040_bridge_is_active()`: `usb_host_rp2040_bridge_task_start()`が実際に成功した時だけ`true`になる`s_bridge_active`フラグのgetter。他backend(MAX3421E/native OTG)使用時に誤ってコマンドを送らないためのガード

### ESP32側(`power_manager.c`)

- 既存のWiFiサスペンド処理と**独立した**トグルで制御。`power_manager_task`内、`wifi_manager_suspend()`の直後に`rp2040_bridge_active() && rp2040_sleep_action_enabled()`を満たせば`usb_host_rp2040_bridge_send_sleep()`を送信、resume時に対称的に`_send_wake()`
- 3つの新規weak extern(`usb_host_rp2040_bridge_is_active`/`_send_sleep`/`_send_wake`、`mruby_filter_usb_suspend_rp2040_sleep_enabled`) - 既存の`mruby_filter_usb_suspend_wifi_sleep_enabled`と同じ理由(この.cはDEVICE/HOST両ロールでコンパイルされるが、参照先はHOST限定の別ファイル)

### mruby DSL(`mruby_filter.c`/`.h`)

- `usb_suspend_rp2040_sleep true/false` - **デフォルト`false`**(既存の`usb_suspend_wifi_sleep`はデフォルト`true`なのと対照的)。理由: 実機未検証の新機能で、RP2040がdormant化すると接続HID機器が実質切断扱いになり復帰後の再列挙遅延・最悪ハングのリスクがあるため、明示的opt-inとした

### RP2040側(`rp2040_host_bridge.ino`)

- 受信処理を新規実装(それまで`Serial1.available()`/`Serial1.read()`を一切呼んでいなかった)。ESP32側と対の状態機械(`feed_cmd_byte()`)で`BRIDGE_CMD_SLEEP`/`_WAKE`をパース
- `enter_rp2040_dormant()`: `BRIDGE_CMD_SLEEP`受信で呼ばれる。処理内容は「設計からの変更点」参照
- LED_BUILTIN(先行実装済みのHIDマウント連動LED、commit `80b36a7`)と統合: dormant突入時に強制消灯、復帰後は既存の`update_hid_led()`(マウント数ベース)で状態を復元

## 設計からの変更点

プランでは「pico-extrasの`sleep_run_from_dormant_source()`/`sleep_goto_dormant_until_pin()`を参考に自前実装」としていたが、実装時にpico-sdk自体に公式の後継ライブラリ`pico_low_power`(pico-extrasの`pico_sleep`を置き換えたもの)が存在し、このArduinoコアにも同梱されていることが判明。`low_power_dormant_until_gpio_pin_state()`一発で済むはずだったが、**採用を見送った**:

- `pico_low_power`の`low_power.c`はTinyUSB対応コードを含む(`tuh_deinit()`/`tuh_init()`をdormant前後で呼ぶ)。これがArduinoコア同梱の`libpico.a`内にビルド済みで格納されており、リンク時にTinyUSB本体(`tusb.c`等)を`libpico.a`から引きずり込んでしまう
- 本スケッチは`Adafruit_TinyUSB_Arduino`(USB Host動作に実際に使う、スケッチごとに別コンパイルされる完全なTinyUSBコピー)を使っており、両者が競合して`multiple definition`でリンクエラーになる
- この非互換は本プロジェクトのUSBスタック構成(`USE_TINYUSB_HOST`)に固有の問題と判断し、`pico_low_power`は使わず、base pico-sdk API(`hardware/clocks.h`/`hardware/gpio.h`/`hardware/pll.h`/`hardware/xosc.h`)だけを使った手組み実装に戻した

`enter_rp2040_dormant()`の実際の手順:

1. `clock_configure()`で`clk_ref`/`clk_sys`をPLL経由からXOSC直結に切り替え(PLLの参照元が消える前に離脱させておく - ここを端折るのが`raspberrypi/pico-extras#41`の既知の「dormantから正しく復帰しない」不具合の実体)
2. `clock_stop(clk_adc)`/`clock_stop(clk_usb)`、`pll_deinit(pll_sys)`/`pll_deinit(pll_usb)`
3. RXピンをGPIO入力に切り替え、`gpio_set_dormant_irq_enabled(pin, GPIO_IRQ_EDGE_FALL, true)`で武装
4. `xosc_dormant()` - ここでブロック。GPIOエッジで結晶発振が再開すると関数自ら戻ってくる
5. `gpio_acknowledge_irq()`→`clocks_init()`(`pico/runtime_init.h`、コールドブート時と同じクロック再構築ルーチン)→`Serial1.begin()`で復帰

ROSCは一度も止めていない(dormant元はXOSC)ので、`pico_low_power`のROSCソース dormantパスと違い`rosc_restart()`は不要と判断し呼んでいない。

## ビルドで踏んだハマりどころ

1. **`hardware/rosc.h`がこのArduinoコアのinclude pathに無い**: `platform_inc.txt`/`core_inc.txt`を直接grepして判明。`hardware_pll`/`hardware_xosc`/`hardware_gpio`/`hardware_clocks`はcore_inc.txtにあるが`hardware_rosc`は無い。ROSCを一切操作しない設計にしたため実害なし(そもそも不要と判明)
2. **`clocks_init()`は`hardware/clocks.h`ではなく`pico/runtime_init.h`にある**: 最近のpico-sdk(rp2350世代も同梱するバージョン)で`runtime_init_clocks()`ベースの初期化に再編されており、`clocks_init()`は後方互換の`static inline`ラッパーとして`pico/runtime_init.h`に残っている。`pico_runtime_init`はcore_inc.txtに含まれておりinclude自体は問題なし
3. **`pico_low_power`のTinyUSB依存によるリンクエラー**: 上記「設計からの変更点」参照。`nm lib/rp2040/libpico.a`で`low_power_dormant_until_gpio_pin_state`が定義済みシンボルとして存在することを確認してから実装→ビルドで初めて発覚。GitHub上のpico-sdkソース(`pico_low_power/low_power.c`)を直接読んで`LIB_TINYUSB_HOST`条件コンパイルが原因と特定

## 未検証・今後の課題

- 460800bpsのUART start bit(約2.17us)がdormant wakeのエッジ検出として確実に機能するか(パルス幅要件) - 実機で有効化して動作した(1回のsleep/wake往復は成功)が、繰り返し耐性・エッジケースは未検証
- RP2040がUSB Hostとしてself-poweredデバイスへの給電を続けている場合、dormant化で接続機器から見て切断扱いになり再列挙が必要になる可能性(遅延の実測は未実施)
- 長時間の繰り返しsleep/wakeサイクルでの安定性(クロック再構築のたびに何らかのリークや状態のズレが蓄積しないか)
