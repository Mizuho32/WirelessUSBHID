# RP2040をHostとして使う方式への移行

`mds/usb_hid/2026-08-23_filter_conv_router_with_max3421.md`からの続き。MAX3421Eが実機で不安定(SPI通信の乱れ、type-c出力追加時のクラッシュ)な上、電源実験で壊れた可能性が高い。RP2040(TinyUSB Host、`rp2040_host_check/`で7バイート届くこと実証済み)をUARTブリッジ経由のHostバックエンドとして採用した。計画・実装の詳細は`mds/usb_hid/2026-08-23_rp2040_as_host_bridge_plan.md`参照。

## 現状(2026-08-23)

- **UDP経路: OK** — ESP32・RP2040とも外部電源を接続し、Device role基板でPC操作できることを確認済み。
- **type-c直結: まだ動かない** — type-cをPCに接続(外部電源なし)すると、PC側で「ESP32 Wireless KVM」として検出はされる(クラッシュはしない、以前の`Unhandled interrupt`は今回は再発せず)が、実際のキーボード/マウス操作は効かない。Device role基板を繋いでもUDPが飛んでいなさそう。

起動ログ:
```
TinyUSB: TinyUSB Driver installed on port 0
USBDEV_TYPEC: USB Device (type-c) started - waiting for a PC to enumerate it...
MAIN_HOST: System ready - forwarding USB HID input to 192.168.0.178:4210
```

## ピン配置の修正

ESP32-S3にGPIO17/18は存在しないため、`usb_host_rp2040_bridge.c`のブリッジUARTピンをGPIO5(TX)/GPIO6(RX)に変更(MAX3421用RST/INTピンと同じ番号だが、両バックエンドは同時に使わないので問題なし)。

## ESP32だけ再起動するとマウント状態を見失う問題(解決)

RP2040を再起動せずESP32だけ焼き直すと、type-c/UDPどちらも無反応になる症状があった。原因: `tuh_hid_mount_cb`はUSB接続の瞬間に1回しか発火しないので、ESP32だけ後から起動するとその1回きりのMOUNTイベントを完全に取りこぼし、`find_mouse_device()`が常にNULLになって`dispatch_report()`が素通りしていた(実機で「マウス抜き差しで直る」ことを確認して特定)。

**対策**:
- RP2040側(`rp2040_host_bridge.ino`): マウント中デバイスを`tracked_devices[]`に記録し、2秒おきにMOUNTフレームを再送。
- ESP32側(`usb_host_rp2040_bridge.c`): `register_mouse_device`/`register_consumer_device`を冪等化(同じdev_addr/idxなら新規追加せず上書き)。

## type-c接続時のクラッシュ(解決)

マウス操作するとPCのカーソルが一瞬動いてクラッシュする問題があった。数段階の切り分けを経て根本原因に到達:

1. 最初のクラッシュは`task_wdt`(IDLE1)。バックトレースを`addr2line`でデコードすると`esp_intr_alloc`関連のフレームが見えたが、`-Og`最適化で関数が誤帰属してる疑いが強く、この時点では確証を持てなかった。
2. 次に`assert failed: tlsf_free ... block already marked as free`(ヒープの二重解放)が発生。バックトレースの`ELF file SHA256`が手元のビルドと一致することを確認した上でデコードすると、`esp_intr_free()`の内部実装(`intr_free_for_other_cpu`等)であることが確定。
3. `dwc2_esp32.h`の`dwc2_int_set()`(`esp_intr_alloc`/`esp_intr_free`を呼ぶ関数)を冪等化(既に確保/解放済みならスキップ)したが、症状は変わらず(のちにこれ自体は正しい対症療法だったと判明、原因の"連打"を止めていなかっただけ)。
4. 冪等化ガードに「スキップした時だけ」ログを追加したところ、**呼び出し元が`usb_host_rp2040`(=ESP32側のブリッジタスク自身)**であることが判明——`bridge_task`はTinyUSBのAPIを直接呼ばないはずなのに、という手がかりから深掘り。
5. `tud_deinit()`(`dcd_int_disable`の唯一の正規呼び出し元)の入口に`esp_backtrace_print()`を仕込んで再現させたところ、今度は同じ`tlsf_free`クラッシュが**`tud_deinit()`を経由せず**再現し、このときの完全なバックトレースが決め手になった:
   ```
   tinyusb_device_task → tud_task_ext → osal_queue_receive(osal_none.h!) → usbd_int_set
     → dcd_int_disable → dwc2_int_set → esp_intr_free → (二重解放)
   ```
6. **根本原因**: `components/tinyusb/host_config/tusb_config.h`に`CFG_TUSB_OS`の定義が無く、`tusb_option.h`のデフォルトフォールバックで`OPT_OS_NONE`(RTOSなし/ベアメタル扱い)になっていた。`osal_none.h`のキュー実装は、排他制御に**USB割り込み自体のdisable/enable**(`esp_intr_alloc`/`esp_intr_free`経由)を使う設計——ベアメタルなら正しい手法だが、これが`tud_task_ext()`のループのたびに(1秒に何十回も)呼ばれ、1回きりのセットアップ/後片付け用の重い関数を連打することになり、レースして二重解放していた。MAX3421オンリーの頃は`tud_task()`自体を回してなかったので顕在化せず、type-c出力(`usb_device_typec.c`)が実際にHIDレポートを流し始めて初めて表面化した。

**修正**: `components/tinyusb/host_config/tusb_config.h`に`#define CFG_TUSB_OS OPT_OS_FREERTOS`を追加。本来のFreeRTOSキュー/ミューテックス実装に切り替わり、割り込みdisable/enableの連打自体が解消。診断用の`esp_backtrace_print()`・詳細ログは撤去し、`dwc2_int_set()`の冪等化ガードだけ保険として残した。

**実機確認**: type-cクラッシュ解消、マウス操作がPCに届くことを確認。

## 現状の課題: type-c直結の遅延がひどい

type-c直結(WiFi経由のUDPより本来低遅延なはず)なのに、UDP経由より体感で遅い。RP2040単体でのUDP転送は特に遅延を感じなかったので、type-c特有の何かがおかしい。raw reportダンプ等のデバッグログ出力(UART0コンソールへの同期出力)がボトルネックになっている疑いがあり、次はログを削って計測する。
